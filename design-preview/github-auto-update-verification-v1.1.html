一、v1.0 之后改了什么

① 发布 1.6.1 —— 让修复真正到达用户

v1.6.0 发布于本地 13:23，而 SSL 修复提交在 14:44，晚了 1 小时 21 分。 线上那个 1.6.0 自带的更新器仍会 PKIX 失败。

1.6.1 把修复带出去。因为老版本更新器自己更新不了自己， 老用户需要手动装一次整包 —— Release 说明里写明了。

② 修掉「跨版本补丁被一律拒绝」

依赖比对原先逐字比较 cfg 的 classpath 行，而 jpackage 文件名里的 hash 每次构建都不一样 → 老用户一律被判定「这个版本更新了依赖」。

改成先抹掉文件名末尾的内容 hash，再比「依赖的名字 + 版本集合」。

坑 4 · 跨版本补丁根本走不通 —— jpackage 文件名里的 hash 不稳定

jpackage 给每个 jar 起的名字是 <名字>-<版本>-<内容hash>.jar， 而这个 hash 每次构建都不一样。元凶是 skiko-awt-runtime-windows-x64-0.7.85 这个包：它只有 293 字节（一个空壳 + 25 字节的 MANIFEST），Compose 插件每次构建都重新压一遍， zip 里条目的时间戳跟着构建时间走 → 字节不同 → hash 不同。 实测同一个版本号 0.7.85，三次构建拿到三个不同的 hash：

bfa84136b65ded4ecdfbe715e20e91a （1.6.0）
841d382d82e6fdf9897ae89b773e4c9 （第一次 1.6.1）
9bd9ae59e7a15e553c56eec0e260fadb （修完代码再构建）

dependencyLines 原先逐字比对，于是 1.6.0 的用户装 1.6.1 时被判 「这个版本更新了依赖，需要重新安装整包」 —— 而实际一个依赖都没动。 换句话说，「应用内下载补丁并自动替换」这条路跨版本从来没成功过。

为什么之前的冒烟发现不了：它把同一次构建的产物复制一份当「老安装」， 两边 cfg 天然一致，永远撞不上。这正是「验收要用真的旧版本当输入」的价值。

修法：比对前先把文件名末尾那段 hash 抹掉（正则 -[0-9a-fA-F]{16,}\.jar$），比的是「依赖的名字 + 版本集合」—— 加依赖、删依赖、升版本照样能认出来，纯粹的内容/时间戳差异不再误报。
抹 hash 是安全的：改写 cfg 时以本地 cfg 为基底，本地依赖行原样保留， 本地那些 jar 叫什么名字都不影响升级后的启动。
坑 5 · 重建目录版报「文件被占用」，其实是 launcher exe 只读

createDistributable 重建时报：
Unable to delete directory … app\StuMate\StuMate.exe
This might happen because a process has files open or has its working directory set in the target directory.

这句提示会把人往「有进程占着」上带（我就这么误判了一次，还去查了进程路径）。 真实原因：jpackage 打出来的 launcher exe 带只读属性（-r-xr-xr-x）， 而 Kotlin 的 deleteRecursively() 不会清只读位， 删到那个 exe 就失败。旁证：同一批删除里，所有 jar 都被删掉了 —— 如果有进程真的在跑，classpath 上的 jar 是会被 JVM 持有的，删不掉。

修法：构建前先手动删掉 app/（Git Bash 的 rm -rf 会清只读位）， 或者干脆换一个全新的构建目录。
顺带纠正 用 Win32 QueryFullProcessImageName 实测：本机跑着的实例在 F:\DownloadQQ\unpacked\StuMate\，跟几个构建目录都没关系。

三、安卓端验收（沿用 v1.0 的 5 张，本轮零改动）

安卓端这一轮没有改动，验收证据与 v1.0 相同： 起点是模拟器上真实装着的 1.4，装一个也走 release 签名、 自称 1.5 的包，让它去对真实的 v1.6 Release 走完整链路。

为什么验收包也必须用 release 签名：debug 签名和正式签名不同， 系统安装器会直接 INSTALL_FAILED_UPDATE_INCOMPATIBLE —— 那样测的就不是更新链路，而是「签名不匹配」。

五、本轮踩到的五个坑

坑 1 · 装了「GitHub 加速」工具的用户，自动更新是静默失效的

本机装了 SteamTools / Watt Toolkit（Steamcommunity302），它对 api.github.com 做透明 TLS 中间人，根证书只装进 Windows 证书库，没进 JDK 的 cacerts。症状：
浏览器、Python、curl 全部正常，只有 Java 应用报 PKIX path building failed。

这类工具在中文用户里装机量很大，而且恰好就是为了访问 GitHub。

修法：把 JDK cacerts ∪ Windows-ROOT 倒进 同一个 KeyStore，再建唯一一个 TrustManagerFactory。

踩过的错误修法 SSLContext.init(null, arrayOf(tmA, tmB), r) 不是「两个都试」： JDK 内部 SSLContextImpl.chooseTrustManager() 只取数组里第一个 X509TrustManager，后面的静默丢弃。拼完照样 PKIX 失败， 现象和没改一模一样。
坑 2 · 截图假阴性：.preview-classpath 指着旧 class 目录

项目里同时有 build/ 和隔离目录 F:/DownloadQQ/stumate-altbuild/， 而 .preview-classpath 里存的是前者（旧的），最后一次真正编译却发生在后者。 结果截图看起来一切正常，只是新加的东西一个都不在。白跑两轮。

修法：shoot_scenarios.py 加 check_fresh() —— classpath 里最新 .class 必须比源码里最新 .kt 还新， 不满足直接报错，不截一张假的图。
坑 3 · 网络抖动是真的会发生的

实测四次下载坏了两回：一次 HTTP 502、一次 HTTP/2 连接被重置。 国内直连 objects.githubusercontent.com 本来就不稳。

修法：给查 Release 与补丁下载加 retrying(times = 3) （间隔 800 / 1600 ms），重试前把半截文件删掉再写。

坑 4（jpackage 文件名 hash 不稳定）与坑 5（launcher exe 只读） 见上面第二节的方框 —— 它们直接决定了「补丁这条路能不能走通」。

六、已知限制 / 待办

  • 桌面 1.6.0 的用户需要手动装一次 1.6.1（自举死结）： 老版本自带的更新器带着 PKIX 缺陷，检查不出新版本。 1.6.1 的 Release 说明里写明了这一步。之后再发新版本就能自动走了。
  • 1.5 及更早的桌面端 / 安卓端没有更新器，用户必须手动装一次新版本。
  • 桌面端装在 %ProgramFiles% 下需要管理员权限（写 app/ 会被拒）。 代码里已经识别 AccessDeniedException 并降级为「打开下载页」。
  • 新版本真的改了依赖（加 / 删 / 升版本）时补丁覆盖不了，会降级为 「需要重新安装整包」。这条由依赖行比对把关，不靠人记得； 比对前会抹掉文件名里的内容 hash（见坑 4）。
  • 更新说明（Release body）目前直接渲染纯文本，没做 Markdown 排版。
  • 桌面端没有做过一次「从 UI 上真的点一下『立即更新』」的验收： 验收环境鼠标注入不可用，替换链路是靠 updateSmoke 断言覆盖的。
