1本轮四项 UI 调整

① 登录 / 注册切换时高度不再跳

「注册」比「登录」多一整块「邀请码」，原来切标签页时对话框会猛地长高，密码框、分隔线、GitHub 按钮、底部按钮全部跟着往下跳 —— 鼠标底下的按钮会自己跑掉。 现在内容区锁死 412dp：表单区顶部对齐、页脚贴底，多出来的高度由「邀请码」那块吃掉。

实测四种状态的元素坐标（像素级扫描截图得出）：

顺带修掉一个会被裁掉的报错 原来错误提示放在可滚动区里。「注册」态本来就被邀请码占满高度，再加一条报错就会超出可滚动区，报错被裁在底下看不见 —— 而报错恰恰是用户此刻唯一需要看到的东西。 现在错误条移到滚动区之外，且因为表单区是 weight(1f)，它吃掉的是表单区的余量，连分隔线都不会动（上表最后两列可见）。

② 隐藏 Google 登录

服务端还没配 Google 的 OAuth 凭据，点了只会拿到 PROVIDER_NOT_CONFIGURED。摆一个必然失败的按钮是骗人，所以登录对话框和「第三方账号」绑定处都撤掉了。 接口层与 startOAuth 的 google 分支都还在，凭据配好后加回一行即可。

③ GitHub 按钮放大 + 内嵌官方标识

从原来和 Google 并排的紧凑按钮（约 150dp 宽）改成 整行全宽、40dp 高，图标与文字一起居中。 标识是手写的矢量路径（GitHubMark.kt）—— material-icons-core 里没有品牌图标， 而那些在 material-icons-extended，本项目构建是 --offline 的加不了依赖。 纯几何数据，不增加任何构建负担；单一 path + 非零填充，所以能被 Icon(tint = …) 整体染色，深色主题下不会「黑猫压深底」。

④ 密码显隐改用表情符号

「显示 / 隐藏」两个汉字在 420dp 宽的对话框里太抢眼，换成 👁️ / 🙈。已放大验证过渲染： 本机 Skiko 走 Segoe UI Emoji，出的是全彩表情（棕色虹膜的眼睛），不是黑白豆腐块。

2GitHub 授权报错：原因与修法

你在浏览器里看到的
Be careful! The redirect_uri is not associated with this application. The application might be misconfigured or could be trying to redirect you to a website you weren't expecting.

这是 GitHub 侧的 OAuth 应用配置问题，不是客户端代码问题。 客户端把服务端给的地址原样打开，服务端也确实传了 redirect_uri，只是 GitHub 那边没登记这个回调地址，于是拒绝授权。

实测服务端返回的授权地址解出来的参数：

参数值
client_idOv23liahl5KxfqpIYXyd
redirect_urihttps://deeer.online/api/stumate/v1/oauth/github/callback
scoperead:user user:email
state32 字节随机串，一次性，10 分钟有效

怎么修

第 1 步 —— 打开 https://github.com/settings/developers， 先看 OAuth Apps 列表里有没有 client_id 为 Ov23liahl5KxfqpIYXyd 的那个应用；找不到就切到 GitHub Apps 标签页找。

第 2 步 —— 把回调地址字段填成（一字不差）：

https://deeer.online/api/stumate/v1/oauth/github/callback

字段名取决于应用类型：OAuth App 里叫 Authorization callback URL；GitHub App 里在 「Identifying and authorizing users」下面，叫 Callback URL。

第 3 步 —— 保存。改完立即生效，不用重启服务端 —— 这个校验是 GitHub 做的，不是你的服务端做的。

容易踩的坑 · 协议必须是 https，域名必须是 deeer.online（不能用 IP，证书 SNI 不匹配）
· 路径是 /api/stumate/v1/oauth/github/callback，结尾不能多一个斜杠
· 不能只填 https://deeer.online —— GitHub 要求精确匹配完整路径
· 如果那里原来填的是 http://localhost:3000/callback 之类的占位地址，就是它了
· 客户端一行都不用改，改完直接重试「使用 GitHub 登录」即可

3截图验收

4几条值得单独说的设计约束

约束为什么
refresh 先落盘再返回服务端对 refresh 做了轮转 + 重放检测。先返回、落盘晚一步，进程此刻崩溃 = 下次拿旧令牌重放 = 整台设备令牌链作废。
并发刷新加互斥锁 + 双重检查两个协程同时刷新会各自拿到新令牌，后落盘的覆盖先落盘的 —— 又是一次重放。
只有 401 才降级为未登录网络故障保持登录态，只是「离线」。否则地铁里打开应用就被登出，用户会以为数据丢了。
令牌用 DPAPI 加密落盘Windows 的 DPAPI 把密钥绑到当前用户账户，别的用户/机器拿到 credentials.bin 也解不开。JNA 直接调 crypt32，不引入原生依赖。
登录接口不校验密码长度若登录对短密码返回 BAD_REQUEST、长密码返回 BAD_CREDENTIALS，就能靠返回码差异枚举账号。冒烟测试专门锁住了这条。
