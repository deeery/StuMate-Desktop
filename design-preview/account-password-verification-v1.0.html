1. 这件事到底做了什么

原先用 GitHub 注册出来的账号，password_hash 是 NULL， 而改密接口必须先验原密码 —— 于是这类账号没有任何途径能设上密码， 只能永远靠第三方登录。

本次新增 POST /auth/password/set：带着 access token 调一次， 设上密码（顺便可以把邮箱改成自己记得住的）。设完之后， GitHub 登录和邮箱密码登录指向的是同一个账号，随时可换着用。

为什么两种方式天然指向同一个账号

GitHub OAuth

绑定挂在 user_id 上，不依赖邮箱。所以改邮箱不会动第三方绑定， 两种登录方式在数据层就已经收敛到同一行了 —— 这不是靠界面「凑」出来的效果。

3. 两个对话框

3.1 设置邮箱密码 —— 还没密码时

深色
浅色
  • 邮箱预填且可改 —— GitHub 常常只给 12345+user@users.noreply.github.com 这类私有转发地址，用户自己记不住， 不许改就等于「设了也登不回来」。
  • 底部三个按钮：忘记密码 / 取消 / 设置。 「忘记密码」直接接到已有的重置码流程。
  • 两次输入不一致当场拦下 —— 服务端算 scrypt 很贵（64 MB 内存）， 不该为了一个打错的确认框跑一趟。
  • 「设置」按钮在必填项不满足时置灰，不是点了才报错。

3.2 修改密码 —— 已经设过了

深色
浅色
这一版走的是 POST /auth/password（验原密码）， 不是 reset-with-code。后者要管理员发重置码，是「忘了密码」的补救， 拿它当「我想改密码」的正路是错的 —— 界面上叫「修改密码」，就该验原密码。

为什么拆成两个对话框，而不是一个带可选「原密码」的表单

  • 没设过密码的用户根本没有「原密码」这回事， 让他面对一个填不出来的字段只会困惑。
  • 已经设过密码的用户走 set 会拿到 409， 服务端不给任何补救路径 —— 必须能进 modify。
  • 拆开后两条路各自的必填项都是确定的，也不存在「我这次到底是新建还是修改」的歧义。

为什么「一旦有密码就永久关闭 set」是硬边界： 少了这道闸，任何拿到 access token 的人都能直接改密码 —— 「改密要验原密码」这条会被整个绕开。这不是偷懒，是必须的安全边界。

4.2 顺带修掉一个真实缺陷：设备重复计数

截图过程中撞上登录超时，排查发现：login 路由无条件 INSERT 一条新设备。 于是一台电脑反复登录，每点一次就多一条设备记录，点满 5 次就被自己的 DEVICE_LIMIT 锁死 —— 而用户从头到尾只有一台机器。

实测数据：该账号名下 5 台设备里有 4 条都叫 WIN-TLLCHC604HH。

改动说明
findOrCreateDevice() 新增。同机（user_id+name+platform）重复登录复用原记录， device_id 不变 → 名下已签发的 refresh 令牌不受影响
hasDevice() 新增。给上限判断用
上限判断 改成 count >= LIMIT && !hasDevice(...) —— 只拦新增设备，不拦同机重登
OAuth callback 同步改。首次 OAuth 注册那处仍用 createDevice —— 用户刚建，设备必然是新的

验证：同一台机器连登 7 次

凭证文件为什么要多存一个字段

旧版本写下的凭证文件里没有 has_password。这里按 true 兜底 —— 宁可少提示一次，也不要凭空告诉一个已经设过密码的人「你还没设密码」。 真实值由紧随其后的 refreshMe() 从服务端取回。

6. 顺手修掉的另一个既有 bug

/me 的 PATCH 原来只回 {id, nickname}， 客户端拿它整个替换 user 对象 → 改完昵称邮箱就变空白。

修法：抽出统一的 publicUser() helper，GET / PATCH / login / register / OAuth callback 全部走它，字段集从此一致。

7. 顺手修掉的截图工具假阴性

原脚本死等固定秒数后截图。登录慢一点就截到「未登录」， 看起来像功能没做，实际只是没等够 —— 假阴性比不截更糟。

改成：预览进程登录成功后给窗口标题打 ready 后缀， 脚本轮询这个信号；等不到就当失败报出来，不产出废图。

效果：同两个场景，从「5 分钟超时 0/2」变成「33 秒完成 2/2」。

8. 待你拍板

① 设置对话框里的「邮箱」是否允许编辑

当前实现是预填 + 可改。理由是 GitHub 常给 …@users.noreply.github.com 这类私有转发地址，用户记不住。 若你希望只读展示，一行可回退。

② 修改密码后是否保留其他设备的登录态

当前服务端行为：改密后吊销除当前设备外的全部令牌 （revokeAllForUser），界面提示「其他设备已下线」。 这是偏安全的选择；若你希望温和些，可以改成只轮转不吊销。

③ 预览用的 preview-nopass@deeer.online 是否保留

它是 password_hash = NULL 的模拟账号，专门用来截 「已登录 + 还没设密码」这个状态 —— 这个状态用登录接口构造不出来 （密码是登录的前提）。删掉的话以后截这个场景要重新造。
