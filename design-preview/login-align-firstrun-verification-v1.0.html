登录强制对齐首端配置 + 首启引导改版 · 验收页 v1.0

桌面端（Compose Multiplatform 1.5.10 / Kotlin 1.9.20）。两件事：
① 每次主动登录都强制把本地对齐到「最早登录那台设备」的配置，被覆盖的那份先备份；
② 首次启动推荐登录 / 注册，但保留游客选项 —— 无边框灰字，在、但不抢眼。

二、登录强制对齐（逻辑改动）

环节行为
触发信号 AccountSession.loginEpoch —— 只有 login() / register() / 第三方登录成功才自增。 restore() 与令牌注入不动它。
为什么不用登录态当信号 signedIn 在「启动恢复」和「主动登录」两种情况下都会 false→true。 拿它当信号会把每次开软件也变成每次清库 —— 那正是刚修掉的缺陷。
对齐动作 syncOnce(forceAlign = true) 的第 0 步先问 SyncApi.status(token)： 服务端 courses > 0 || notes > 0 → 跳过 push，直接 「备份 → 清空 → 全量拉」。
为什么必须跳过 push 照常先 push 的话，本地这份分歧会先污染服务端，对齐就落空了。
服务端为空时 必须照常 push。否则 initial_device_id 永远是 null， 谁都成不了首端，之后所有设备都拿不到「以谁为准」的答案。
用户可见反馈 同步卡显示「已对齐首端配置 · 拉取 N 条」，并保留被覆盖配置的备份路径。
启动同步去重 startOnLaunch() 加了 launchSyncDone 幂等守卫 （Compose 1.5.10 实测 effect 会在键值未变时重复执行），resetForSignOut() 时清掉。

登录强制对齐端到端 桌面端未做破坏性端到端（见下方说明）；同一套逻辑已在移动端真机跑通

为什么桌面端跳过破坏性端到端：该路径的动作是「备份 → 清空 → 全量拉」， 会直接改写 %APPDATA%\StuMate\ 里的真实用户配置，而桌面应用此刻正在运行、 持有同一个 SQLite 文件。收益（验证一段 12 行、与移动端逐字同源的逻辑） 抵不上风险。引擎层的 forceAlign 分支已由 160 项单测覆盖， 整条链路的行为一致性由移动端真机验证背书。
