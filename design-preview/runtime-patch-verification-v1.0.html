「检查更新」永远报 PKIX —— 根因与修复验收

StuMate 桌面端 · 1.6.1 → 1.6.2 · 验收页 v1.0 · 2026-10-06

一句话：打包用的 jlink 裁剪运行时漏了 jdk.crypto.mscapi， 导致读不到 Windows 系统根证书库；本机装着 SteamTools（GitHub 走中间人）， 于是「检查更新」必然失败 —— 而异常被 runCatching 吞掉， 用户只看到一句 PKIX path building failed，完全指不出根因。

本次做了两件事：① 补上模块并把它变成「不可再漏」； ② 让补丁包也能替换 runtime/ —— 否则代码修好了也送不到用户手上。

1. 现象

1.6.1 安装版在「设置 → 软件更新」点「检查更新」，稳定失败：

× 检查失败
查询最新版本 失败（已重试 3 次）：PKIX path building failed:
  sun.security.provider.certpath.SunCertPathBuilderException:
  unable to find valid certification path to requested target

同一台机器上 ./gradlew run（开发态）永远正常。

2. 根因

2.1 三条独立证据

检查项结果
jimage list runtime/lib/modules | grep -i mscapi 无输出 —— 模块不在镜像里
runtime/conf/security/java.security:77 写着 security.provider.12=SunMSCAPI —— 配置以为它在
全量 JDK 下 KeyStore.getInstance("Windows-ROOT") 读到 73 条证书（含 SteamTools 两条）—— 证书库本身没问题

链条：缺模块 → SunMSCAPI provider 不注册 → Windows-ROOT 抛 KeyStoreException → 被 runCatching 吞掉 → 静默退回默认 SSLContext → 只剩一句 PKIX。

2.2 A/B 实测：同 jar、同 JDK 17.0.12，只差 runtime 模块集

做法：把 createDistributable 的产物复制两份，cfg 的 app.mainclass 指向运行时探针 UpdateProbeKt， B 组只把 runtime/ 换成缺 mscapi 的那套。

A 组 runtime 含 jdk.crypto.mscapi

更新检查探针
  java.home      = …\StuMate-probeA\runtime
  sslDiagnostics = 尚未构建   ← 尚未构建
  sslDiagnostics = jdk=148 os=73
  state          = UpToDate(current=1.6.1)
√ 系统根证书库已并进信任链

B 组 runtime 缺该模块

更新检查探针
  java.home      = …\StuMate-probeB\runtime
  sslDiagnostics = 尚未构建   ← 尚未构建
  sslDiagnostics = 构建失败：KeyStoreException:
                   Windows-ROOT not found
  state          = Failed(… PKIX path building failed …)
× 系统根证书库没读进来

os=73 与 2.1 里「全量 JDK 读到 73 条」完全一致 —— 说明 A 组真的把 系统库读进来了。

2.3 为什么「只在打包产物里出现」

./gradlew run / IDE 用的是系统 JDK 的完整模块集， 这个 API 一定正常。只有 jpackage 那个被 modules(...) 裁剪过的 runtime 才会抛异常 —— 而异常又被吞了，所以本地怎么试都是「好的」。

3. 修复（一）：补上模块，并让「再漏」不可能静默

① build.gradle.kts 的 modules(...) 加一行

modules(
    "java.sql", "java.logging", "java.naming", "java.prefs",
    "java.management", "java.xml", "java.net.http",
    "jdk.unsupported",
    "jdk.crypto.mscapi",   // ← 补上
)

缺它的症状与当初漏 java.sql 一模一样：都是「异常被吞 + 只在打包产物暴露」。

② UpdateCenter 新增 sslDiagnostics —— 把静默降级变成可诊断

每个失败分支都记下信任链的构建结果，TLS 类失败时把诊断串附在错误信息里。 修复后 B 组那种安装报的错会自带一行：

查询最新版本 失败（已重试 3 次）：PKIX path building failed …
（本机信任库：构建失败：KeyStoreException: Windows-ROOT not found）

用户截图就能看出断在哪一层，不必再查半天。

③ JlinkModulesTest —— 跨文件断言，不靠人记得

直接解析 build.gradle.kts 的 modules(...) 块， 断言必须含 jdk.crypto.mscapi；并反向守卫「解析出的模块集不是空壳」 （防止正则失效导致「因为错误的原因通过」）。另有两条运行时断言。

4. 修复（二）：让补丁包能替换 runtime/

为什么必须做：1.6.1 的补丁包只含 app/ 下 2 个文件。 就算发了 1.6.2 补丁，用户点「立即更新」之后 runtime 还是坏的那个 —— 「检查更新」照旧报 PKIX。代码修好了送不到用户手上，等于没修。

新格式

条目什么时候带大小
app/StuMate-Desktop-<版本>-*.jar + app/StuMate.cfg总是约 2 MB
runtime/release总是（它写着「这个版本期望的模块集」）247 B
runtime/lib/modules只在模块集真的变了时约 15 MB（压缩后）
runtime/ 下其它变化文件随基准比对自动带上很小

客户端拿补丁里的模块集与本地比：不同 → 换；相同 → 不动（省下 15 MB 流量）。 打包端 release.py 自动挑 dist/ 里更早的最大版本 portable zip 当基准。

为什么能在运行时替换一个「正在被用着」的文件

runtime/lib/modules 是 jlink 的模块镜像，启动时被打开并按需映射。 实测它可改名、可写、甚至可删（JDK 打开时带了 FILE_SHARE_DELETE）：

--- 1) 改名 (os.rename) ---
  [OK]   rename modules -> modules.locktest
--- 2) 直接覆盖写 (open 'wb') ---
  [OK]   可写：前 16 字节已清零
--- 3) 删除 (os.remove) ---
  [OK]   remove modules

但「允许」不等于「可以随便写」：不能直接覆盖内容（本进程还映射着它， jimage 懒加载，后面才加载的类会炸）；改名是安全的 （只动目录项，旧 inode 继续被映射）。所以实现是「先全部写 .new， 再统一改名」。

runtime/bin/ 与 lib/server/ 下的 native 库是真锁死的 （Windows loader 加载），规则是只允许新增 —— 补 mscapi 会多出 bin/sunmscapi.dll，那是新增，安全。

顺序上的两个讲究

  • runtime 替换放在主 jar 之前：失败时还什么都没动，用户重试即可； 反过来先换 jar 再失败，就正好复现「新 jar 配旧 runtime」这个形态。
  • runtime/release 最后落盘：它是启动自检唯一的依据。 先落盘而 modules 换失败会让安装「谎报健康」，比明显坏掉更难查。
绕不过去的自举问题：1.6.1 自带的更新器不认识 runtime/ 条目，会静默跳过 —— 用户点了更新、重启了、问题照旧，且无任何提示。 所以 1.6.1 用户必须手动装一次 1.6.2 整包。 为此加了 runtimeGapOfSelf()：设置页常驻检查装好的 runtime 缺不缺必需模块， 缺就明确说「请下载整包重新安装一次」。从 1.6.2 起这种安装不再无声无息。

8. 复跑方式

# A/B 探针（打包产物里跑，才看得出这个坑）
cp -r <目录版产物> probeA && cp -r <目录版产物> probeB
